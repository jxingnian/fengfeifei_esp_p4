# AI Opus 音频链路

## 后台配置

输入和输出均可选择 `pcm` 或 `opus`；当前 ES8311 采集/播放路径要求
`sampleRate=16000`、`channel=1`、`bitDepth=16`。不支持的配置会明确拒绝，
不会把压缩码流直接作为 PCM 播放。后台字段以 `xn_ai_server/src/coze.ts`
的 `deviceAudioConfig()` 为准。

Opus 上行固定为 60ms、960 samples、24kbps、VOIP、VBR。每个 WebSocket
binary 消息携带一个编码包，不添加小智专用协议头。下行按后台
`output.frameSizeMs` 配置解码；建议使用 20ms 或 60ms。当前期望后台传递
有包边界的裸 Opus 数据，不是 Ogg 文件流；不能把多个没有边界的裸 Opus 包
直接拼接后解码。解码器按照 `raw.consumed` 消费数据并拒绝无进展或坏包。

## 速率与容量

| 数据 | 连续采集时的理论值 |
| --- | --- |
| 原始 PCM | 16000 × 2 = 32000 bytes/s（31.25 KiB/s） |
| 当前采集 chunk | 512 samples、1024 bytes、32ms、31.25 次/s |
| Opus 编码输入 | 960 samples、1920 bytes、60ms、16.67 帧/s |
| Opus 目标负载 | 24000 / 8 = 3000 bytes/s（2.93 KiB/s，VBR 实际可变） |

以上不含 WebSocket/TLS/TCP 开销，不是网络实测速率。旧日志只显示队列满，
不能据此精确计算上行带宽。

网关音频 TX/RX 各 160 项，控制 TX/RX 各 64 项；业务播放音频 96 项、
控制 32 项。额外的原始 PCM 编码队列为 4 项（240ms），满时同样丢最旧帧。
上行 160 个 60ms 包最多积压约 9.6 秒，因此扩大队列仅用于
吸收抖动，不代表低延迟；持续拥塞时仍会丢弃最旧音频。

参考本地 `xiaozhi-esp32/main/audio/audio_service.h` 和 `.cc` 的 60ms
Opus、压缩发送缓冲和满队列丢旧包策略。小智发送队列为 40 项（2.4 秒），
本工程按扩大队列的要求使用 160 项；未移植小智整个音频引擎。
采集回调只拼帧并零等待入队，`voice_ai_enc` 独立任务执行编码和上行入队，
下行解码/播放及控制在 `voice_ai` 业务任务执行。PCM 模式也由编码任务按
60ms 裸 PCM 分片上行，不在采集回调中发送。

小智 `main/audio/audio_service.cc` 为 `opus_codec` 任务分配 `2048 * 12`
即 24KiB 栈。本工程 `voice_ai_enc` 使用 32KiB（VOIP、complexity=5），
解码/控制任务使用 24KiB，原麦克风/唤醒任务仍为 8KiB。SILK 编码函数内部
还有大栈帧，仅将 PCM/Opus 缓冲移到静态内存并不能避免内部用栈溢出。
本次崩溃对应固件的反汇编显示，`silk_encode_frame_FIX` 入口先减少 SP
1280 bytes，再在崩溃地址 `0x4013c4fe` 减少 8192 bytes，仅该函数就申请
9472 bytes，超过原采集任务的 8192 bytes，尚未计入上层调用及后续子函数。

## 队列与会话语义

- 音频和控制消息分队列；普通控制优先，`audio_stop`/`error` 优先中止。
- `audio_end` 有顺序屏障：必须先交付/播放它之前的音频，防止提前关闭功放。
- 音频队列满时丢最旧包，接纳新包；单个编码、入队、发送、解码或播放失败
  只丢当前包，不主动结束会话。底层真正断线仍按正常重连流程处理。
- 控制消息满队列不是音频丢包：网关保留重连保护，业务层重置会话，避免
  丢失开始/结束事件后留在错误状态。
- 会话结束/切换播放时清理旧上行队列并使旧代音频失效；已在发送中的帧无法撤回。
- 编码句柄创建/重配与编码处理由编码互斥锁保护；采集使用另一把短时拼帧锁，
  不等待编码。切换配置/会话时清空 PCM 队列并递增代号；编码前、发送前都
  校验代号，防止旧会话的在途 PCM 在新会话中发送。
- 编解码输出缓冲静态分配且对齐，不占用任务栈；入队的网络重组缓冲
  缩小到实际消息长度，避免一个小 Opus 包长期占用 16KB。

## 日志与实机验证

约每 5 秒按实际窗口长度输出：

- `AI 音频生产`：原始采样数/速率、采集回调、编码帧数/帧率、编码待发字节/速率、
  下行解码数、业务丢弃数和播放队列深度。
- `AI 音频上行速率`：成功写入 WebSocket 的音频帧数/字节/速率、TX 队列深度、
  TX 丢弃数、发送失败数和网关 RX 丢弃数。这不是服务器已收到的确认值，
  也不包含传输协议开销。切换播放时主动清队列也计入 TX 丢弃数。
- `AI 编码任务首帧完成` / `AI 任务栈`：编码和解码/控制任务的最低剩余栈字节，
  以及 PCM 编码队列深度。ESP-IDF 的 `uxTaskGetStackHighWaterMark` 返回字节，
  不是标准 FreeRTOS 文档中的字数。编码尚未运行时显示 0 不代表已经溢出。

验证顺序：

1. 确认启动日志显示 `输入=opus，输出=opus，16000Hz/单声道/16bit`。
2. 连续说话 10 秒，对比生产/成功发送速率。稳定全窗口原始速率接近
   31.25 KiB/s、编码约 16.67 帧/s；VBR 字节数可变。唤醒/播放切换的窗口
   并非全程采集，速率较低是正常的。确认首帧完成，检查最低剩余栈量；
   若低于 4096 bytes，应先评估并增加对应任务栈，再继续长时测试。
3. 确认回复能完整播放到末尾；分别测试 20ms/60ms 下行、多轮回复及打断。
4. 模拟弱网/拥塞：观察队列深度、丢弃/失败计数，单包失败不能立即触发
   “AI 会话结束”；真实断线应重连并重新获取 ready 配置。
5. 测试停止会话和视频通话抢占，确认旧音频不会在下一轮继续发送/播放。

构建通过只能证明接口和链接正确，不能替代上述硬件、音质与网络验证。
