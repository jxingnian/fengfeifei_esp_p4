二、当前实际音频链路
当前链路是：
麦克风 PCM
  -> 60 ms 分帧
  -> 本地 VAD
  -> Opus 编码
  -> Base64 + WebSocket 上传

Coze WebSocket
  -> conversation.audio.delta
  -> Base64 解码
  -> audio_callback
  -> ai_dialog 音频队列
  -> PCM 队列
  -> ES8311/I2S
但是目前存在一个确定的格式错误：
1. 项目配置下行编码为 Opus：[coze_app.c (line 164)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\coze_app\\coze_app.c:164)
2. Coze SDK 收到下行数据后只做 Base64 解码，没有 Opus 解码：[esp_coze_chat_event.c (line 54)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\managed_components\\espressif__esp_coze\\src\\esp_coze_chat_event.c:54)
3. SDK 的 CMake 中也没有任何 Opus 解码依赖：[CMakeLists.txt (line 1)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\managed_components\\espressif__esp_coze\\CMakeLists.txt:1)
4. 项目却把回调数据标记为 PCM，并直接送入扬声器：[coze_app.c (line 275)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\coze_app\\coze_app.c:275)、[ai_dialog.c (line 391)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\ai_dialog\\ai_dialog.c:391)
也就是说，当前播放队列接收的不是 PCM，而是 Opus 压缩帧。当前代码把 Opus 字节直接当作 int16_t PCM 写入 I2S，这是链路中的首要错误。
三、为什么会大量返回并溢出
当前 Coze 配置是：
下行编码：Opus
单帧时长：20 ms
周期：1 秒
每周期最大帧数：50
对应配置位于 [coze_app.c (line 167)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\coze_app\\coze_app.c:167)。
50 帧 × 20 ms = 1 秒音频。这个配置本身等价于“每秒最多返回 50 个音频帧”，不是“每 20 ms 必须严格返回一个包”。Coze 的 limit_config 是服务端时间窗口上限，不是播放同步协议。
当前应用又有以下事实：
- Coze 回调没有播放确认，也没有反向流控：[coze_app.c (line 252)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\coze_app\\coze_app.c:252)
- WebSocket 回调只把数据快速放入 s_audio_queue
- s_audio_queue 长度为 96：[ai_dialog.c (line 36)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\ai_dialog\\ai_dialog.c:36)
- 队列满时不会等待，而是丢弃最旧数据，再尝试加入新数据：[ai_dialog.c (line 253)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\ai_dialog\\ai_dialog.c:253)
- PCM 队列只有 4 项：[ai_dialog.c (line 38)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\ai_dialog\\ai_dialog.c:38)
- 播放开始前还固定等待 120 ms：[ai_dialog.c (line 420)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\ai_dialog\\ai_dialog.c:420)
因此“溢出”的直接原因是：
Coze 按服务端窗口快速下发
  -> SDK 回调没有播放流控
  -> 应用非阻塞入队
  -> 队列满后丢弃旧音频包
当前 sdkconfig 中统计日志是关闭的，所以固件不会周期性打印 RX drops 数量：[`sdkconfig` (line 4456)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\sdkconfig:4456)。
四、Coze 配置是否有问题
下行 20 ms + 50 帧 配置不是语法错误，但它不能保证“边播放边严格匀速返回”。
真正的配置问题有两个：
1. mode 使用了 ESP_COZE_CHAT_SPEECH_INTERRUPT_MODE，这是正确的。
2. 但项目自己的 server_vad 被硬编码为 false：[coze_app.c (line 286)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\components\\coze_app\\coze_app.c:286)。
而 SDK 在 Speech Interrupt 模式下实际会发送服务端 VAD 配置，快速模式为 500 ms：[esp_coze_chat_protocol.c (line 266)](D:\\XingNian\\client\\17_Yuefei501\\fengfeifei_code\\fengfeifei_AI_bot_esp32\\esp_ai_p4_c5\\managed_components\\espressif__esp_coze\\src\\esp_coze_chat_protocol.c:266)。
结果是：
Coze 服务端：启用了 server_vad
本地 ai_dialog：仍按 client VAD 逻辑运行
这会导致输入链路和 Coze 服务端状态机不一致，但它不是下行音频包溢出的根因。下行溢出的根因是“没有真实播放流控 + 当前队列满后丢包”。
五、能不能慢慢返回、一边播放一边返回
Coze 当前这个 SDK 没有播放确认接口，不能做到：
设备播放完一帧
  -> 通知 Coze
  -> Coze 再返回下一帧
只能通过以下方式实现稳定播放：
1. 修正下行格式：把下行改成 PCM，或者正式加入 Opus 解码器。
2. 保留独立播放环形缓冲区，按 I2S 实际消耗速度播放。
3. 不在 WebSocket 回调中执行阻塞播放。
4. 增加高水位保护，缓冲区达到上限时停止当前回复或发送取消，而不是静默丢弃音频。
5. 统一 server_vad 配置，避免服务端 VAD 和本地 VAD 同时控制同一轮对话。
当前最优先的正式修复顺序是：
先修正 Opus/PCM 格式错误
  -> 再统一 server_vad
  -> 再重构下行播放缓冲与高水位策略
